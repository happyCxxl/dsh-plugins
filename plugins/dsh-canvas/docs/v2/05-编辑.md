## 3. 子项 5.1 · 样式写到哪里 ✅

### 决定：产物内独立一个"编辑覆盖"样式块

在 `index.html` 的 `<head>` **末尾**追加一个带固定 id 的 `<style>`，所有手工调整集中写入其中：

```html
<head>
  <link rel="stylesheet" href="design-tokens.css">   <!-- 令牌：不动 -->
  <style>/* 页面自身样式，由生成阶段产出 */</style>

  <!-- 编辑覆盖层：编辑器唯一写入的位置 -->
  <style id="cv-edits">
    body > section:nth-of-type(2) > button:nth-of-type(1) { padding: 20px; }
    body > section:nth-of-type(4) > h2:nth-of-type(1) { color: #b8553a; }
  </style>
</head>
```

| 项 | 做法 |
|---|---|
| **选择器** | 自动生成的 `nth-of-type` 路径（`02` §6 已定：**不靠模型标注**） |
| **位置** | `<head>` **末尾** → 优先级高于页面自身样式，但**令牌仍然生效**（因为覆盖层只写具体属性，不重定义令牌） |
| **清空** | 删掉整个 `#cv-edits` 块即**恢复全部手工调整** |
| **漂移处理** | 若元素结构变化导致某个选择器命不中，**该条规则自动失效**（无害），并在编辑器里提示"这条调整已失效" |

### 为什么不写内联样式

| | 内联样式 | `#cv-edits` 覆盖块 |
|---|---|---|
| 改动位置 | **散落到各标签的 `style` 属性里** | **集中在一个块里** |
| 优先级 | 最高，**盖住令牌** → 换肤时该元素不跟随 | 高于页面样式，**不破坏令牌关系** |
| 一键还原 | 要逐个标签清理 | **删掉一个块** |
| 与 `04` §3 校验 | 无差别 | 无差别 |

> **实测说明**：参考方案（design）**没有**类似的"编辑覆盖块"机制（`data-ipw-edit` / `ipw-edits` / `editStyle` / `overrideStyle` 在其 Studio bundle 里**全为 0**）。它的**令牌编辑**用注释边界做文本级替换（`/* ipw-theme:start */ … /* ipw-theme:end */`），而**元素级样式编辑最可能是内联**——这一路径未能从静态分析确认。**因此本项是我们的设计选择，而非照抄。**

### 令牌编辑走另一条路

改主题（`design-tokens.css`）**不经过 `#cv-edits`**，而是直接改令牌文件的注释边界内那一段：

```css
/* cv-theme:start */
:root { --cv-color-primary: #5b50e6; /* … */ }
/* cv-theme:end */
```

理由（`01` §7.3 已定）：令牌是**唯一换肤入口**，必须集中、可精确替换、不必解析 CSS。

**于是编辑器有两个写入目标，职责分明**：

| 目标 | 改什么 | 影响范围 |
|---|---|---|
| `design-tokens.css` 的令牌段 | 主题性值（颜色、字体、圆角、间距…） | **全局** |
| `index.html` 的 `#cv-edits` 块 | 单个元素的几何与外观 | **单个元素** |

## 4. 子项 5.2 · 撤销机制 ✅

### 两个不同粒度的机制，都要有

| 机制 | 粒度 | 持久性 | 用途 |
|---|---|---|---|
| **内存撤销栈** | **每一次操作**（改个颜色、改段文字） | 当前会话内；**刷新即失** | 编辑过程中 Ctrl+Z 逐步退 |
| **git 版本** | **点保存时**一个 commit | **永久**，可随时回退 | 回到"上周那版" |

**这两个不能互相替代**：

- **git 不能当撤销用**——粒度太粗。用户改错一个颜色不该产生一个 commit
- **内存栈不能当版本用**——刷新就没，且没有历史

### 流程

```
编辑操作 → 立即作用于预览副本 + 压入内存撤销栈（不落盘）
   ↓
Ctrl+Z → 弹栈，还原到上一步
   ↓
点「保存」→ 写回产物文件（index.html 与/或 design-tokens.css）→ 一次 git 提交
   ↓
点「回退」→ 从版本历史取回某次提交的内容，作为新提交写入（02 §8 已定）
```

### 编辑期的写入目标是哪里

**编辑过程不直接写产物文件。** 预览走内存副本（`02` §4 已定：内联依赖 + `srcdoc`），编辑作用于该副本；**只有「保存」才落盘**。

好处：
- 编辑中随时可以放弃（不落盘 = 产物没变）
- 避免"改一半保存了"的半成品状态（与 `04` §5"不留半成品"一致）
- `mtime` 冲突检测（`02` §8）只需在保存时做一次

## 5. 子项 5.3 · 编辑范围 ✅

### 做

| 类别 | 内容 |
|---|---|
| **文字** | 直接编辑文本内容（`contentEditable` 式就地编辑） |
| **样式** | §6 的 15 个属性（写入 `#cv-edits`） |
| **链接** | 编辑 `href`（仅页内锚点或安全 URL） |
| **主题** | 编辑 `design-tokens.css` 的令牌（全局换肤） |

### 不做（明确边界，各有理由）

| 不做 | 理由 |
|---|---|
| **拖拽 / 缩放** | 用户明确表示不需要；且它依赖绝对定位，容易把页面改坏 |
| **对齐、多选、图层顺序** | 复杂度高、收益低 |
| **结构增删**（加节点 / 删节点 / 复制节点） | **这正是"对话修改"该做的事**——agent 改结构比人拖更可靠 |
| **图片上传 / 替换** | 产物必须自包含；换成什么资产应由对话决定 |
| **字体族选择** | 自包含约束下不能引外部字体，本机字体对跨机器呈现不可控 |
| **定位方式与旋转** | 会改变布局流，且与响应式冲突 |

### 与"对话修改"的分工

| | 对话修改 | 可视化编辑 |
|---|---|---|
| 适合 | 结构变化、新增区块、交互调整、文案重写 | 微调（间距、颜色、字号、一句文字） |
| 粒度 | 大 | 小 |
| 可靠性 | agent 理解意图，能处理连带影响 | 直接作用于目标元素，无理解成本 |
| 共同点 | **都走同一套产物与版本机制** | |

**两者不是二选一，是互补**：可视化编辑解决"就差一点点"，对话修改解决"要改意思"。

## 6. 子项 5.4 · 属性集（15 个）✅

| 类别 | 属性 | 说明 |
|---|---|---|
| **尺寸与间距** | `width` `height` `padding` `margin` | 纯数字自动补 `px`（参考方案同样做法） |
| **颜色** | `color`（文字）`background_color` | 文字色与元素底色分开，避免歧义 |
| **字体** | `font_size` `font_weight` `line_height` `letter_spacing` | 均为单元素可独立设置 |
| **对齐** | `text_align` | |
| **边框与装饰** | `border`（有无 / 颜色 / 宽度）`radius` `shadow` `opacity` | |

### 为什么不多不少

**纳入标准（三条同时满足）**：

1. **可在单个元素上独立设置**（不牵动布局流）
2. **效果一眼可见**（所见即所得）
3. **不引入外部资产、不改变文档结构**

**排除项与理由**：

| 排除 | 理由 |
|---|---|
| `position` / `rotation` | 改布局流，与响应式冲突 |
| `font_family` | 涉及外部字体，与自包含冲突 |
| `fill` 渐变 / 图片 | 渐变需配色协调，图片涉及资产——交给对话 |
| `lock` / `unlock` | 单人使用，防误编辑收益低 |
| 删元素 / 复制元素 | 结构增删归对话修改 |

> **与参考方案的对比**：design 的属性面板约 **17 个样式字段**（含 `position` / `rotation` / `font_family` / 渐变 / 图片）。我们取其中 **13 个**并补 **2 个**（`line_height` 与 `letter_spacing` 独立列出、`margin` 与 `padding` 明确分开），共 **15 个**。差异全部来自上表的三条纳入标准。

### 数值处理

纯数字自动补 `px`（如输入 `20` → `20px`）；带单位的输入原样保留（如 `1.5rem`、`50%`）。**参考方案同样如此**。

## 7. 编辑后是否重跑校验

`04` §3 定了两道校验（完整性 + 渲染检查）。

| 时机 | 是否跑 |
|---|---|
| 每次编辑操作 | **不跑**（会卡顿，且编辑中状态本就不完整） |
| **点保存时** | **跑渲染检查**（能开、无 JS 异常、无资源失败、无横向溢出） |

**为什么保存时才跑**：编辑过程是内存副本，跑校验没有意义；保存才是"产生一个新版本"的时刻。**渲染检查不过 → 不保存、不提交**（与 `04` §5"不产出产物"一致）。
