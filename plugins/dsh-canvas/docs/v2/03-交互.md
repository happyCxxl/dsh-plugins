## 3. 子项 3.1 · 是否需要交互 ✅

### 决定

**由模型根据需求判断**，并把这个判断**显式写进 `manifest.json`**：

```jsonc
{ "interactive": true,                    // 需要交互
  "interactions": "interactions.json" }   // 为 true 时必须存在
```

| 情形 | 规则 |
|---|---|
| `interactive: true` | **必须**存在 `interactions.json` 且非空；每条交互都要通过验证 |
| `interactive: false` | **必须不存在** `interactions.json`；且产物 HTML 里**不得有行为脚本** |

### 为什么是"可证伪的自我声明"

模型做判断（有的场景确实只要纯展示，如"关于我们"），但**判断本身要被检查**——否则"声明无交互"就会变成逃避验证的漏洞。声明为假却被扫出行为逻辑 → 报错。

### 为什么不做"一律必须有交互"

会给纯展示页强加无意义的交互，且会诱导模型**编造交互来过关**（正是要防的"交了个静态壳子说能交互"的反面）。

## 4. 子项 3.2 · 交互如何声明与验证 ✅

### 4.1 根本方向：`interactions.json` 是**产物输入**，不是测试脚本

```
interactions.json   声明：这个页面有哪些交互
        ↓
模型读它，在产物 HTML 里实现这些交互
        ↓
验证器读它，去真实浏览器里确认这些交互真的实现了
```

**关键差异**（与常见"步骤 + 断言"式测试契约）：

| | 步骤 + 断言式 | 本方案 |
|---|---|---|
| 文件内容 | 命令式步骤 + 期望断言 | **只有交互清单** |
| 谁定"期望什么" | 写文件的人手写 | **验证器从交互语义推导** |
| 模型负担 | 要写"怎么测" | **只写"有什么交互"** |

**文件里没有期望、没有断言。** 既然声明了"切换到年付"这个交互，那么"操作它应产生可观察变化"是**该交互的定义**，不需要再声明一遍。

### 4.2 文件位置与形状

位于产物目录，与 `manifest.json` 平级：

```jsonc
// canvas/<产物名>/interactions.json
{
  "schemaVersion": 1,
  "interactions": [
    {
      "id": "billing-yearly",          // 机器用：与 data-cv-* 挂钩
      "name": "切换到年付",             // 人用：失败报告与提交信息
      "trigger": [                     // 动作数组（单动作即长度为 1）
        { "action": "click", "selector": "#billing-toggle" }
      ]
    },
    {
      "id": "email-invalid",
      "name": "邮箱格式非法时被拦截",
      "trigger": [
        { "action": "clearAndType", "selector": "#subscribe-email", "value": "not-an-email" },
        { "action": "click", "selector": "#subscribe-submit" }
      ]
    },
    {
      "id": "tabs-switch",
      "name": "切换标签页前先展开高级选项",
      "preconditions": [               // 前置动作：仅搭建状态，不验证
        { "action": "click", "selector": "#toggle-advanced" }
      ],
      "trigger": [ { "action": "click", "selector": "#tab-billing" } ]
    }
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 稳定标识；**必须**与产物里的 `data-cv-interaction` 值一致 |
| `name` | ✅ | 人类可读，1..96 字符，文件内唯一 |
| `preconditions` | — | 前置动作序列：**仅搭建初始状态，不参与验证** |
| `trigger` | ✅ | 动作数组（至少 1 个）；**这是被验证的那串操作** |

### 4.3 `preconditions` 与多动作 `trigger` 的分工（避免实现时歧义）

两者都能表达"先做 A 再做 B"，**职责必须分清**：

| | `preconditions` | `trigger` |
|---|---|---|
| **目的** | 把页面带到某个**起始状态** | 执行**本交互本身** |
| **失败处理** | 失败即该交互**无法建立初始态** → 报"前置失败"（诊断指向前置动作） | 失败即该交互失败 |
| **是否参与"变化"判定** | **否**——基线在 `preconditions` 全部执行**之后**采集 | **是**——变化是相对基线而言 |
| **使用建议** | 仅在"该交互确实依赖先前状态"时使用 | 表达交互本身的完整操作序列 |

**因此**：能用 `trigger` 数组表达的连续操作，**优先用 `trigger`**；只有"这部分不属于本交互、但必须先做"时才用 `preconditions`。

### 4.4 挂钩：产物如何与声明对应

产物 HTML 里用 `data-cv-*` 标记（与 `02` §6 的寻址层一致）：

```html
<!-- 触发元素：标上交互 id -->
<button id="billing-toggle" data-cv-interaction="billing-yearly">按年付费</button>

<!-- 受影响元素：标上同一个 id -->
<div id="saving-note" data-cv-effect="billing-yearly">已切换到年付，按 10 个月计价</div>
<p id="price-pro" data-cv-effect="billing-yearly">¥949</p>
```

| 标记 | 加在 | 作用 |
|---|---|---|
| `data-cv-interaction="<id>"` | **触发**该交互的元素 | 验证器据此定位触发点 |
| `data-cv-effect="<id>"` | 该交互**会影响**的元素（可见性、文本、属性、类名、数量） | **告诉验证器该看哪里**，避免它去猜 |

> `data-cv-effect` 的必要性：没有它，验证器只能靠"触发前后整个页面有任何变化"来判断，**误判率高**（无关的动画、时间戳、闪烁都会被当成"有变化"）。

### 4.5 动作白名单（全集）

**动作要尽可能全**（用户明确要求）。参数见"参数"列。

#### 鼠标

| 动作 | 参数 | 说明 |
|---|---|---|
| `click` | — | 单击 |
| `dblclick` | — | 双击 |
| `contextmenu` | — | 右键 |
| `mousedown` / `mouseup` | — | 分开的按下 / 抬起（长按、拖拽需要） |
| `hover` | — | 移入并停住 |
| `mouseover` / `mouseout` | — | "经过"与"离开"（区别于停住） |
| `drag` | `to` | 拖到目标元素 |
| `dragBy` | `dx`, `dy` | 按位移拖拽（滑块、画布） |
| `wheel` | `dy` 或 `dx` | 滚轮（缩放、横向滚动） |
| `clickWith` | `modifiers: [ctrl\|shift\|alt\|meta]` | 修饰键点击（多选等） |

#### 键盘

| 动作 | 参数 | 说明 |
|---|---|---|
| `type` | `value` | 逐字符输入 |
| `clearAndType` | `value` | 先清空再输入（避免旧值干扰） |
| `press` | `key` | 单键（`Escape` / `Enter` / `Tab` / `ArrowUp` …） |
| `hotkey` | `keys: [...]` | 组合键 |
| `focus` / `blur` | — | 聚焦 / 失焦（触发校验、展开、收起） |

#### 表单

| 动作 | 参数 | 说明 |
|---|---|---|
| `select` | `value` | `<select>` 选值 |
| `check` / `uncheck` | — | 勾选 / 取消 |
| `setChecked` | `checked: bool` | 显式设定勾选态 |
| `setValue` | `value` | 直接赋值（**绕过键盘**，用于 `range` / `date` / `color` 等） |
| `submit` | — | 提交表单（含原生校验路径） |
| `reset` | — | 重置表单 |

#### 页面

| 动作 | 参数 | 说明 |
|---|---|---|
| `scrollTo` | `selector` | 滚到元素（触发懒加载、吸顶） |
| `scrollBy` | `dy` | 相对滚动 |
| `navigateHash` | `hash` | **页内**锚点跳转（`01` §8 已定不做跨页） |
| `wait` | `ms` | **时序控制，非用户动作**；上限 **5000ms** |

**`wait` 的地位**：它是动作白名单的一员，但语义是"等"而不是"用户做了什么"。设上限是为了防止它被滥用成"等一等总能过"。

### 4.6 不纳入的动作（明确记为后续扩展）

| 动作 | 为什么暂不纳入 |
|---|---|
| `tap` / `swipe` / `longPress` | 需要 CDP 的移动端模拟（`Emulation.setDeviceMetricsOverride` + `setTouchEmulationEnabled`）。当前视口矩阵**只改尺寸、不改触摸能力**，故暂不纳入；移动视口下仍验证布局与可点击性 |
| 画布自由绘制（含压感、笔类型、多点触控） | `dragBy` 已覆盖基本情形；压感与多点触控无法可靠验证 |
| 媒体播放控制 | 依赖编解码与用户手势策略，结果不稳定 |
| 文件上传 | 需构造文件对象，收益低 |
| 剪贴板读写 | 权限与安全策略复杂，结果不稳定 |

### 4.7 验证：两道，各自机械可判

#### 第一关 · 结构交叉校验（不需要浏览器）

| 检查 | 判据 |
|---|---|
| 声明完整性 | 每条有 `id`、`name`、至少一个 `trigger` 动作；`id` 与 `name` 文件内唯一 |
| 动作合法性 | 所有动作在 §4.5 白名单内，且参数字段合法（如 `wait` 的 `ms ∈ [0,5000]`） |
| **声明与产物一致** | 每个 `id` 在产物里**恰好有**至少一个 `data-cv-interaction="<id>"` |
| **影响面存在** | 每个 `id` 至少有一个 `data-cv-effect="<id>"`（否则无法判定"有变化"） |
| 可达性 | `data-cv-interaction` 元素**可达**：非 `display:none`、非 `hidden`、非 `aria-hidden`、尺寸非零 |
| 选择器存在 | 所有 `selector` 在产物 DOM 里能命中 |

#### 第二关 · 真实浏览器行为验证

执行环境：**真实 Chrome + CDP over pipe**（照抄参考方案：不用端口 / WebSocket；**不截图**；Chrome 缺失时返回独立的 `skipped`，**不伪装通过**）。

| 检查 | 判据 |
|---|---|
| **① 有可观察变化** | 执行 `trigger` 后，**至少一个** `data-cv-effect="<id>"` 元素在 文本 / 可见性 / 值 / 属性 / 类名 / 数量 之一上发生变化 |
| **② 确定性** | 同样操作**重复两次**得到同样结果 |
| **③ 初始态不是终态** | 触发前该效果**尚未满足**（排除"一打开就已经是某交互结果"的错位） |
| **④ 零外部请求** | 全程无外部网络请求（与自包含约束一致） |
| **⑤ 无运行时错误** | 无未捕获 JS 异常、无 console error |
| **⑥ 多视口成立** | 移动 / 桌面 / 宽屏矩阵下都成立 |

**基线采集时机**：`preconditions` 全部执行**之后**、`trigger` 执行**之前**（§4.3）。

#### `interactive: false` 时的验证

不跑第二关的交互部分，改为断言：

1. `interactions.json` **不存在**
2. 产物 HTML 里**没有行为脚本**（无 `<script>`、无内联事件处理器）

### 4.8 这比"步骤 + 断言"强在哪

| 方面 | 步骤 + 断言式 | 本方案 |
|---|---|---|
| 确定性 | 需手写 | **验证器自动补** |
| 初始态检查 | 需手写 | **验证器自动补** |
| 零请求 | 需手写 | **验证器自动补** |
| 模型写错"怎么测" | 常见失败源 | **不存在**（模型不写"怎么测"） |
| 漂移 | 断言与实现不一致 | 用 `data-cv-*` 挂钩挡住 |

## 5. 子项 3.3 · 交互如何推断 ✅

### 需求里交互的两个来源

> 用户原话：「一方面是**页面需要**，另一方面是**根据场景需要**（用户输入或者根据用户输入识别到【推断】）」

| 来源 | 含义 | 例子 |
|---|---|---|
| **页面需要** | 这类页面的常规交互，不做就是残缺 | 定价页必须有月付/年付切换；FAQ 必须能展开 |
| **场景推断** | 从需求里推断出合理的交互 | 用户说"做个订阅页" → 推断出邮箱校验与提交反馈 |

### 实现方式：靠提示词与 Skill 引导，**不做打勾式清单**

**参考方案的做法**（已实测）：

- **Archify**：`SKILL.md` + `references/` **纯文本指引** + **一个 CLI 场景指南**（`archify guide "<场景>" --json`，**只推荐类型与 recipe，不生成图**）
- **design**：`applyChecklist`（每个模板 5 条，Zod 强制 `min(1)`）

**我们的决定**：采用**前者**（指引 + 示例），**不做**后者那种"逐条回应"的清单。

**理由**：清单会让"推断"退化成"打勾"——模型只需要把清单项对上就算完成，而**你要的是从需求真正推断**。清单还必然是不完备的（场景无限），完备性压力会让清单不断膨胀。

**但"引导"必须有约束力**：模型必须**显式作出判断**（写进 `manifest.json` 的 `interactive`），且这个判断**可被证伪**（§3）。**引导负责"想到"，声明负责"负责"。**

### 场景引导的形态

`references/` 里给一份**按页面类型组织的交互提示**，例如：

| 页面类型 | 通常应有的交互 |
|---|---|
| 定价页 | 计费周期切换；套餐对比展开；FAQ 展开 |
| 表单页 / 订阅页 | 字段校验与错误提示；提交后的成功/失败反馈；条件字段显隐 |
| 落地页 | 导航吸顶；锚点跳转；FAQ；CTA 反馈 |
| 看板 / 报表 | 数据筛选；排序；时间范围切换；明细展开 |
| 文档 / 长文 | 目录跳转；折叠章节；代码复制 |

**这不是强制清单，而是提示**——目的是让模型"想到"，最终判断权在模型。

## 6. 子项 3.4 · 提示词 / Skill 设计 ✅

### 两个参考方案的长处（实测对比）

| | **Archify** | **design** |
|---|---|---|
| 载体 | **独立 `SKILL.md`**（YAML frontmatter：name / description / license / metadata） | **无 SKILL.md** |
| 结构 | **渐进式披露**：主文件 + `references/` 按主题拆 | 工具描述 + 对话注入提示词 |
| 入口引导 | `description` 写明**何时启用** | 客户端把上下文填进**对话草稿**，**不自动发送** |
| 操作纪律 | *"A non-zero exit is never success"*、修复轮次有上限、*"Examples teach shape, not facts"* | *"Read the current file before editing. Change only this element unless I explicitly request a wider redesign, preserve unrelated structure and styles, and keep the linked design-tokens.css theme contract."* |
| 按需加载 | *"Read branch references only when their stated trigger applies"* | — |
| 按模板规则 | — | `applyChecklist`（Zod 强制存在） |

### 我们的设计：两者的长处都要

| 层 | 内容 | 学自 |
|---|---|---|
| **`SKILL.md`** | 何时用、工作流顺序、产物形态、**交互推断引导**、硬性纪律 | Archify |
| **`references/`** | 按主题拆分：产物格式契约、交互声明格式、动作白名单、验证规则、门禁、编辑操作、场景引导 | Archify |
| **工具描述** | 字段级说明（更靠近调用点） | 两者 |
| **编辑器注入的提示词** | 选中元素后注入"文件 + 元素 + 定位器 + 原文"，并附**最小改动纪律** | design |

**我们相对两者的演化**：参考方案的"按模板规则"是 `applyChecklist`；**我们的等价物是 `interactions.json` 本身**——交互声明就是那个"必须回应"的东西，而且它**比清单更强**：不是打勾，而是**要真的实现并在浏览器里跑通**。

### 工作流顺序（含样式，顺序不可颠倒）

```
需求
 ↓
① design-tokens.css     先定美学（令牌）—— 交互的"可观察变化"多为视觉变化，令牌先定可避免回头改样式
② interactions.json     声明有哪些交互
③ index.html            实现：结构 + 样式 + 行为（引用令牌；用 data-cv-* 挂钩）
④ brief.json            需求留痕
⑤ manifest.json         元信息（含 interactive 标志）
 ↓
验证：结构交叉校验 → 真实浏览器行为验证 → 版本提交
```

> **一处过程记录**：本文档初稿讨论工作流时**漏掉了第 ① 步（令牌）**，由用户指出后补上。`design-tokens.css` 是独立文件（`01` §7.3），工作流必须包含它。
