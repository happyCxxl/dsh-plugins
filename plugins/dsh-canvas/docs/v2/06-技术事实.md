## 1. DSH / Cordis 集成层

### 1.1 `ctx.<service>` 未声明 `inject` 时读取会**抛异常**

| 项 | 内容 |
|---|---|
| **现象** | 读 `ctx.tools`（未在 `inject` 里声明）抛出 `cannot get property "tools" without inject` |
| **关键陷阱** | **`ctx?.foo` 的可选链抓不住它**——它不是返回 `undefined`，而是**抛**。因此 `ctx?.tools` 一样会炸 |
| **应对** | ① 用到的服务**必须**写进 `export const inject = [...]`；② 需要容错读取时用 `try/catch` 包装（例如 `readService(ctx, name)` 这类包装函数），**不要**指望可选链 |

**推论**：插件加载失败往往不是"逻辑错"，而是**少声明了一个 inject**。诊断时先核对 `inject` 与 `ctx.<service>` 的对应关系。

### 1.2 加载新代码**必须完全重启**，面板开关无效

| 动作 | 能否加载新代码 |
|---|---|
| 插件面板里安装（覆盖文件） | ❌ 只是把文件写到磁盘 |
| 面板里**关闭再打开**插件 | ❌ 会重建 Cordis 插件树，但 **ESM 模块已在 Node 进程里缓存** |
| **完全退出应用再打开** | ✅ 新进程，模块缓存清空 |

**判定方法**（不要靠"感觉生效了"）：比对**磁盘上的文件哈希**与**运行中的行为**。例如让插件在运行期渲染一次并观察产物，与磁盘代码的预期输出对照。

> 旧文档一度写过"面板关一下再开即可生效，不必重启"——**该说法已被推翻**，不要沿用。

### 1.3 `desktop` profile 被 Electron 独占

```
dsh plugin --profile desktop <任何子命令>
→ 报错："profile desktop is managed exclusively by the Electron application"
```

**后果**：桌面版安装插件**只能通过应用内的插件面板**。CLI 安装通道对桌面版不适用。

### 1.4 本地安装用 **tarball**

目录形式的 `add` 有 **junction 悬空**陷阱。本地开发安装应走 tarball：

```
npm pack  →  得到 <pkg>-<ver>.tgz  →  在面板里安装该 tgz
```

### 1.5 `ctx.tools.register(definition)` 的三个契约

| # | 契约 | 实测症状 |
|---|---|---|
| 1 | **必须声明 `output: { schema, render, presentationMeta? }`** | 缺 `render` → 报 `tool "x" must declare output { schema, render, presentationMeta? }` |
| 2 | **`render(args, value)` 必须纯**（可重放，不得有副作用） | — |
| 3 | **JSON Schema 只支持受限子集**：`type` / `oneOf` / `properties` / `required` / `additionalProperties` / `items` / `enum` / `const` + 注解 | **`type` 数组被拒**：`type must be a single type string (type arrays are not supported)` |

**第 3 条的应对**：表达"可空字符串"要用 `oneOf: [{ type: 'string' }, { type: 'null' }]`，**不能**用 `type: ['string', 'null']`。

### 1.6 子代理派发（`ctx.subagents`）

| # | 契约 | 后果 |
|---|---|---|
| 1 | `SubagentStartRequest.parent` 是**必填的存活 `Agent`**，它提供**会话 cwd、谱系与委派深度** | 插件的 `apply(ctx)` 与 HTTP 路由处理器里**没有**存活 Agent；伪造一个（如 `ctx.agents.create({ sessionId })`）会被 `spawn` 直接拒绝 |
| 2 | **工具路径里有真身**：`exec.agent`（来自 `ToolRunContext`）就是**当前会话的活 Agent**；HTTP 路径没有 | 需要"当前会话身份"的能力**必须做成工具**，不能只做 HTTP 路由 |
| 3 | `run.result` 在**子级失败时也 resolve**（`stopReason: 'error'`） | **必须读 `stopReason`** 判断成败，不能靠 `catch` |
| 4 | 能力不匹配会**显式拒绝**（`UNSUPPORTED_CAPABILITY`），而非静默忽略 | 用 `outputSchema` / `toolFilter` 前要先确认 provider 支持 |

## 2. 浏览器与 CDP

### 2.1 CDP over pipe：NUL 分隔，不是行分隔

| 项 | 内容 |
|---|---|
| 启动参数 | `--remote-debugging-pipe` |
| 通道 | **fd 3 = 写命令；fd 4 = 读响应** |
| 消息格式 | **NUL（`\0`）分隔的 JSON** —— **不是**按行分隔 |

**猜错格式的后果**：永远收不到响应（而不是收到坏数据），**很难反查**。

### 2.2 两个 fd 流都必须挂 `'error'` 监听

| 项 | 内容 |
|---|---|
| **现象** | 向已退出的 Chrome 写入 → 触发**异步 `EPIPE`** |
| **为什么 try/catch 抓不到** | 它不是 `write()` 的同步异常，而是流的异步 `'error'` 事件 |
| **后果** | 未处理的流错误**冒泡成进程级 uncaught exception**，整个插件进程挂掉 |
| **应对** | 在 **write 流与 read 流上都**注册 `'error'` 监听，转成可读的 CDP 错误 |

**这条在"可执行文件不存在"或"Chrome 启动即退出"时最先触发**——也就是最需要清晰诊断的时候。

### 2.3 Windows 上要杀**进程树**

```
taskkill /PID <pid> /T /F
```

只杀主进程会留下渲染进程等**孤儿进程**，累积占用资源。

### 2.4 必须给 Chrome 独立 `--user-data-dir`

用临时目录（如 `mkdtemp`），**不要**复用用户的默认 profile。否则：
- 会干扰用户正在使用的 Chrome
- 清理时容易误杀用户自己的进程

**清理注意**：Windows 上删除临时 profile 目录可能遇到 `EBUSY`，需要**重试**。

### 2.5 `srcdoc` 与 `blob:` 的 `baseURI` 问题

| 预览方式 | iframe 文档的 `baseURI` | 相对路径外链 |
|---|---|---|
| `iframe src` → 真实 URL | 产物自己的 URL | ✅ 可解析 |
| `iframe srcdoc` | **宿主页面的 URL** | ❌ 必然失败 |
| `iframe src` → `blob:` URL | **不透明的 blob URL** | ❌ 无法解析 |

**结论**：`srcdoc` / `blob:` **可以用**，但**前提是把依赖内联**（样式表 → `<style>`，图片 → data URI）。设计层面见 `02-产物形态.md` §4。

### 2.6 Node 22.19 自带 zstd 解压

```
zlib.zstdDecompressSync
```

系统上**不一定有** `zstd` 命令行工具，但 Node 内置可用。

## 3. 本机环境侧

### 3.1 全局 DSH 安装损坏（与插件无关）

| 项 | 内容 |
|---|---|
| **现象** | 任意 profile 都报 `cannot create effect on inactive context` |
| **根因** | `LocalSandboxProvider` 在**构造函数**里调用 `ctx.effect()`，而它应在 `apply()` 里调用 |
| **连带** | `dsh-app-boot` 的 `assertEntriesLoaded` 把 `entry.fiber === undefined` 误报为"could not be resolved"，因此错误信息指向错误的方向 |
| **影响范围** | **桌面版不受影响**（它用自带的 runtime） |
| **结论** | 这是**上游缺陷**，在插件侧无法修复；不要在这上面继续投入 |
