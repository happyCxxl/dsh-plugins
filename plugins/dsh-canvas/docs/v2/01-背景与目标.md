# 01 · 需求背景与产品目标

> **状态：✅ 已定稿。** 本文是 v2 的第一个议题，冻结后作为后续议题的前提。
> 解决方案见 §7（实现级规范，无歧义）。

## 1. 出发点的原话

> "我的需求背景是我看到 design 和 archify 这两个插件，我觉得 design 生成的结果页面很好看，但是是静态页面，不是动态交互的，但是 archify 生成的架构图结果也是 html，但是是动态可交互的。
>
> 然后我的最终产品目标和 design 插件类似，即需要满足任意场景需求生成动态可交互的精美页面，然后支持生成后的修改编辑以及版本管理。"

## 2. 从出发点推出的四个必须同时成立的约束 ✅

| # | 约束 | 来源 |
|---|---|---|
| 1 | **任意场景** | 「满足任意场景需求」 |
| 2 | **精美** | 「精美页面」；对标 design |
| 3 | **动态可交互** | 「动态可交互」；design 做不到，这是本产品的差异点 |
| 4 | **可修改 + 可版本管理** | 「支持生成后的修改编辑以及版本管理」 |

**四条是"与"关系，不是"或"。** 只做到其中三条都不算达成目标。

## 3. 关键推论 ✅

### 3.1 为什么"自由编写 HTML"是必需的

design 的实现机制（实测，见 §4）是：**把真实 HTML 文件放进工作区，由 agent 直接编辑**。它的"精美"来自 29 个手工设计资产，"任意场景"来自 agent 可以写任意 HTML。

如果产出只能由程序按预设结构生成，那么**"任意场景"与"精美"同时都做不到**——两者都要求设计自由度。

**结论：agent 直接编写与修改 HTML，是产出的根本方式。**

### 3.2 "精美"与"可交互"是两件独立的事

对照实测：

| 方案 | 精美 | 动态可交互 |
|---|---|---|
| deepseek-idesign | ✅ 29 个模板 + 令牌系统 | ❌ **零功能交互** |
| Archify | — | ✅ |

design 的 29 个模板里：**内联事件 0 个、提交处理 0 个、表单控件 11 个但全部无行为**。它是**设计稿**，不是**能用的页面**。

**结论：本产品的核心命题不是"如何让页面好看"（已被证明可做到），而是"如何让自由写出的 HTML 天然具备可靠的交互"。**

### 3.3 交互需求的两个来源 ✅

> 用户原话：「一方面是页面需要，另一方面是根据场景需要（用户输入或者根据用户输入识别到【推断】）」

| 来源 | 含义 | 例子 |
|---|---|---|
| **页面需要** | 这类页面的常规交互，不做就是残缺 | 定价页必须有月付/年付切换；FAQ 必须能展开 |
| **场景推断** | 从用户的需求里**推断**出合理的交互 | 用户说"做个订阅页" → 推断出邮箱校验与提交反馈 |

**第二类意味着插件不是被动执行，而要主动推断"这个页面还缺什么交互"。**

## 4. 调研实测：两个参考方案的真实机制

### 4.1 deepseek-idesign

| 层 | 实测结果 |
|---|---|
| 资产 | 29 个手工 HTML 模板；**7 类 × 12 风格**（`app` / `article` / `cards` / `other` / `poster` / `report` / `site`；`bold` / `dark` / `data` / `editorial` / `glass` / `minimal` / `newsprint` / `playful` / `retro` / `sketch` / `soft` / `technical`） |
| 最小粒度 | `card-twitter` 3.8KB —— **可以只是一个组件**，不必是整页 |
| 起点 | `+` 选模板，**或 "blank project" 从零开始** |
| 生成方式 | **agent 直接编辑工作区里的真实 HTML/CSS 文件**（README：「真实 HTML、CSS 和项目文件保存在当前 Harness 工作区」） |
| 模板的角色 | 只是起点，负责给"精美"打底 |
| 令牌 | 20 或 24 个声明式变量（`color` / `font` / `number` / `text`，分组 `theme` / `background` / `typography` / `components`）；编辑器据此给出**颜色选择器**而非文本框 |
| 改造规则 | 每个模板强制带 5 条 `applyChecklist`；**Zod 校验 `min(1).max(240)`，缺失即模板非法** |
| 产物位置 | 工作区 `design/<sessionId>/` |
| 附加导出 | 内置 pptxgen / jspdf / jszip / html2canvas |

**关键：没有魔法。** "任意场景"就是"agent 能写任意 HTML"；那 29 个模板只是让**起点**更好看。

### 4.2 Archify

可靠性来自**消除自由度**（模型只写声明式数据，产物由程序确定性生成）。**代价是放弃表达自由**，因此它的适用范围窄（架构图这类结构固定的产物）。

## 5. 产品目标（一句话）

> **在本插件里，产出是工作区中的真实 HTML 文件；agent 可以直接编写与修改它；产物单文件自包含、断网可用、点击有真实响应；每次生成与修改进入版本历史，可随时回退；统一存放于工作区 `canvas/<产物名>/` 下。**

## 6. 已确认的立场 ✅

| # | 立场 |
|---|---|
| 1 | **agent 直接编辑 HTML 文件**是产出的根本方式，不是"模型输出结构化数据、再由程序生成 HTML" |
| 2 | **模板只是起点**，用来保证起点的精美度，**不是必须的**（可以从零写） |
| 3 | 交互需求有两个来源：**页面需要** + **场景推断** |
| 4 | **一个产物 = 一个页面**；可以是一个完整页面，也可以只是一个组件 |
| 5 | **交互仅限于当前页面内**；跨页跳转与路由**不做** |
| 6 | 采用 design 的人工美学作为美学基线（见 §7.1、§7.4） |
| 7 | **不提供基础样式表**：只给令牌变量，HTML/CSS 由 agent 自由编写（见 §7.2） |

## 7. 解决方案（实现级规范，冻结）

> 本节把"精美"如何落地写到**无歧义**的程度，供后续实现直接遵循，**不再另行决策**。

### 7.1 结论一：美学是一个**审美决定**

调研中最反直觉的发现：design 的"精美"**不来自**字号阶梯、间距阶梯、行高配对这类**规范工作**，而来自**一组人工选定的美学值**——硬编码在插件里，不随场景变化。

```js
// deepseek-idesign 插件内嵌的默认令牌（"blank project"从零开始时写入）
const DEFAULT_TOKENS = `/* ipw-theme:start */
:root {
  --ipw-color-bg: #f2f0eb;          // 米色底，不是纯白
  --ipw-color-text: #171717;
  --ipw-color-primary: #5b50e6;     // 有性格的深紫，不是默认蓝
  --ipw-color-accent: #f26b38;
  --ipw-font-display: Georgia, serif;                   // ★ 衬线标题
  --ipw-card-radius: 24px;
  --ipw-card-shadow: 0 24px 70px rgb(24 20 14 / 10%);   // 大而柔的投影
  --ipw-section-space: 96px;
}`;
```

**四个决定贡献了绝大部分"高级感"**：米色底（而非 `#fff`）、衬线标题（而非无衬线）、深紫主色（而非默认蓝）、大而柔的投影。

**反证**：早期实现把精力投入"字号从 13 种收敛到 8 档"这类规范工作，视觉结果"和修改之前没有任何区别"——**规范不产生美**。

### 7.2 结论二：**不提供基础样式表**

| 明确不做 | 为什么 |
|---|---|
| `*{box-sizing}` / `body{margin:0}` 之类 reset | agent 自己会写；预置反而限制自由 |
| `body` / `h1`–`h6` / `p` 的预设排版规则 | **设计自由属于 agent** |
| `.card` / `.btn` / `.grid` 之类组件类 | 预设类名会诱导"所有页面长得一样"——**这正是旧实现的失败原因** |
| 字号阶梯 / 间距阶梯 / 行高档位表 | §7.1：规范不产生美 |

**唯一提供的是 §7.4 的令牌变量。页面自身的 CSS 全部由 agent 编写。**

### 7.3 结论三：令牌与页面是**两个文件**，用注释边界隔离

令牌放在独立文件里（**不内联进 HTML**），理由：换肤只改一个文件、程序可精确替换，且**不必解析 CSS**。

边界标记用注释界定可替换区间：

```css
/* cv-theme:start */
:root { … }
/* cv-theme:end */
```

### 7.4 令牌规范（21 项，冻结）

**前缀 `--cv-`**：与 design 的 `--ipw-` 隔离，两者同页共存不冲突。

**取值**：照搬 design 的默认美学（§7.1），因为**它已被验证能产出用户认可的观感**。

```css
/* cv-theme:start */
:root {
  --cv-color-bg: #f2f0eb;
  --cv-color-surface: #ffffff;
  --cv-color-text: #171717;
  --cv-color-muted: #66645f;
  --cv-color-border: #d7d3ca;
  --cv-color-primary: #5b50e6;
  --cv-color-secondary: #dcd8ff;
  --cv-color-accent: #f26b38;
  --cv-color-on-primary: #ffffff;
  --cv-font-display: Georgia, serif;
  --cv-font-body: Arial, sans-serif;
  --cv-font-size-base: 16px;
  --cv-line-height-body: 1.55;
  --cv-type-ratio: 1.25;
  --cv-content-width: 1180px;
  --cv-page-padding: 32px;
  --cv-section-space: 96px;
  --cv-card-bg: #ffffff;
  --cv-card-border: #d7d3ca;
  --cv-card-radius: 24px;
  --cv-card-shadow: 0 24px 70px rgb(24 20 14 / 10%);
}
/* cv-theme:end */
```

**逐项语义**（分组名与 design 一致）：

| 组 | 令牌 | 语义 |
|---|---|---|
| `theme` | `--cv-color-primary` | 主色：按钮、链接、强调 |
| | `--cv-color-secondary` | 次色：次级块背景、弱强调 |
| | `--cv-color-accent` | 点缀色：徽标、装饰 |
| | `--cv-color-text` | 正文与标题的文字色 |
| | `--cv-color-muted` | 弱化文字：说明、脚注 |
| | `--cv-color-border` | 描边与分隔线 |
| | `--cv-color-on-primary` | **主色底上的前景色**（按钮文字） |
| `background` | `--cv-color-bg` | 页面底色 |
| | `--cv-color-surface` | 卡片/面板底色 |
| `typography` | `--cv-font-display` | 标题字族 |
| | `--cv-font-body` | 正文字族 |
| | `--cv-font-size-base` | 正文基准字号 |
| | `--cv-line-height-body` | 正文行高 |
| | `--cv-type-ratio` | 字号阶梯比例；标题按它放大（`h1 = base × ratio⁴` 这类推导由 agent 决定） |
| `components` | `--cv-content-width` | 内容最大宽度 |
| | `--cv-page-padding` | 页面左右内边距 |
| | `--cv-section-space` | 区块之间的垂直间距 |
| | `--cv-card-bg` | 卡片底色 |
| | `--cv-card-border` | 卡片描边 |
| | `--cv-card-radius` | 卡片圆角 |
| | `--cv-card-shadow` | 卡片投影 |

> 计数说明：以上为 **21 项**（`theme` 7 + `background` 2 + `typography` 5 + `components` 7）。相比 design 的 20 项，**多出 `--cv-font-size-base` 与 `--cv-type-ratio`**（design 用 `--ipw-type-scale` 一个数同时表达这两件事，语义含糊）；去掉了 `--ipw-body-line-height` 的歧义命名（改名 `--cv-line-height-body`）。

### 7.5 三条硬性规则

1. **所有主题化值必须走 `var(--cv-*)`**：颜色、字体、宽度、间距、圆角、投影**不得硬编码**
2. **非主题值可以硬编码**：布局几何、`clamp()` 的具体数值、字号倍数属于设计自由，不受此限
3. **令牌文件是唯一换肤入口**：改主题只改这一个文件，不改 HTML

### 7.6 这样能保证"精美"到什么程度（诚实边界）

| 保障 | 机制 |
|---|---|
| **起点不难看** | §7.4 是一套已验证的人工美学；agent 引用它写出的页面天然带有该观感 |
| **每个页面都能不同** | §7.2：**不给任何预设结构或组件类**，长相完全由 agent 决定 |
| **精美不随场景退化** | 起点资产（模板）只是"更好"，不是"必需"；从零写也有同一套令牌兜底 |

**诚实的边界**：最终观感仍取决于 agent 那一轮写出的 CSS 质量。令牌保证"底色不难看"，**不保证每一轮都是精品**。

这是选择"自由 HTML"必然的代价——与旧实现"**锁死长相、保证下限但上限极低**"是相反的取舍。


## 8. 非目标（明确不做）

| # | 非目标 | 依据 |
|---|---|---|
| 1 | **多页 / 路由 / 跨页跳转** | 用户原话：「永远是一个页面」「跳转其他页面明显涉及到其他页面，这是不需要的」 |
| 2 | **交互跨页面传播** | 用户原话：「对于交互也仅限于当前页面的交互」 |
| 3 | **后端服务、数据库** | 待议题 3（交互范围）复核 |
| 4 | **部署 / 托管 / 分享链接** | 待议题 2（产物形态）复核 |

## 9. 术语

| 术语 | 含义 |
|---|---|
| **产物** | 一个页面（或一个组件）及其伴随文件 |
| **起点 / 资产** | 用于提高起点精美度的预设 HTML；**是可选起手，不是填空模板** |
| **令牌** | §7.4 的 `--cv-*` CSS 变量；唯一的主题化入口 |
| **门禁** | 对产物的自动检查；具体内容见后续议题 |
| **场景推断** | 从用户需求里推断出应主动补上的交互 |
