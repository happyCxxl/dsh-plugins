## 3. 子项 2.1 · 产物是多文件 ✅

### 结论

**产物由多个文件组成**，至少包含：

| 文件 | 作用 |
|---|---|
| `index.html` | 页面本身；通过 `<link rel="stylesheet" href="design-tokens.css">` 引用令牌 |
| `design-tokens.css` | 令牌层；见 `01` §7.3、§7.4 |

### 用户对"单个 HTML 文件"的澄清

早期表述"产物是一个 HTML 文件"**指的是一个页面**（区别于多页站点），**不是文件数量**。

> 用户原话：「这个不需要，可以是甲，因为我说的单个 html 文件一直指的是一个页面」

因此本文档中**"一个产物 = 一个页面"**是语义约定；**文件形态是多文件**。

### 为什么选多文件而不是严格单文件

| 能力 | 为什么依赖令牌外置 |
|---|---|
| **一键换肤** | 改主题只改一个文件，**不碰 HTML**，HTML 不会被写坏 |
| **程序化改样式** | 令牌文件用 `/* cv-theme:start */ … /* cv-theme:end */` 定界，程序可**精确替换**那段，**不必解析整个 CSS** |
| **agent 改页面更安全** | 令牌与页面分离 → agent 改布局时不会碰坏主题 |

**代价（已知并接受）**：**不能只拷走 `index.html`**。只拷 HTML 会导致全部 `var(--cv-*)` 失效——背景、字体、圆角、投影、宽度全部塌掉，页面退化成"裸 HTML"。

> 实测参照：design 的产物正是此形态（`index.html` 1321 字节 + `design-tokens.css`，HTML 里 13 处 `var(--ipw-*)`，1 处外链）。**拷走 HTML 会丢失全部观感。**

### 是否提供"导出单文件"

⬜ **待议**（属子项 2.5 伴随文件清单）。若提供，则"单文件自包含"成为**导出产物的属性**，而非源产物的属性。

## 4. 子项 2.2 · 预览方式 ✅

### 结论

**采用参考方案（design）已验证的做法：内联依赖后注入 `srcdoc`。**

| 场景 | 做法 |
|---|---|
| **编辑预览 / 导出截图** | **把令牌 CSS 内联成 `<style>`、图片转 data URI，再注入 `iframe srcdoc`**，`sandbox="allow-same-origin"` |
| **下载 / 给用户看产物** | 走真实 URL 路由（`/raw?workspaceId=…&path=…`），**用 `fetch` 带 header token** 读取 |

**两种方式并存，各司其职**：预览走内存（不依赖路由与认证，且编辑器能同源访问 DOM），下载走路由（得到文件本身）。

### 关键技术约束：`srcdoc` 必须内联依赖

`srcdoc` 的文档 `baseURI` **继承宿主页面**，因此**相对路径的外链资源一定加载失败**。

同源 HTTP 环境下的实测（同一份产物、同一份外置令牌）：

| 预览方式 | 令牌是否解析 | `border-radius` | iframe 文档的 `baseURI` |
|---|---|---|---|
| `iframe srcdoc`（外链令牌） | ❌ **失败** | **0px** | `…/host`（宿主页的 URL） |
| `iframe src` → `blob:` URL | ❌ **失败** | **0px** | `blob:http://…`（不透明，无法解析相对路径） |
| `iframe src` → 产物真实 URL | ✅ 成功 | 24px | `…/artifact/index.html`（正确） |

**根因**：`href="design-tokens.css"` 是相对路径，相对于**文档的 `baseURI`** 解析。`srcdoc` 的 `baseURI` 是宿主页 → 令牌被解析到宿主目录 → 加载失败。

### 参考方案怎么解决这个问题（实测其代码）

design 的**编辑预览用的就是 `srcdoc`**：

```jsx
g.jsx("iframe", {
  ref: y,
  srcDoc: ut,                     // ← srcdoc
  title: `Design preview: ${Dl(X)}`,
  className: je("border border-border bg-white …")
})
```

它靠**内联**绕开 `baseURI` 缺陷，两个函数分工明确：

```js
// Xh(...)  构造预览 HTML，把令牌 CSS 作为内联 <style> 注入
const p = a.trim()
  ? `<style id="ipollowork-design-template-token-style">${a.replace(/<\/style/gi,"<\\/style")}</style>`
  : "";

// fg(...)  把外链图片下载并内联为 data URI
const d = Array.from(l.querySelectorAll("img[src]")).filter(...);
→ downloadWorkspaceFile(workspaceId, path)     // 带 x-ipollowork-design-token header
→ m.setAttribute("src", dataUri)
→ m.setAttribute("data-ipw-preview-src", 原值)  // ★ 保留原始引用以便写回
```

**`data-ipw-preview-src` 这一手很关键**：内联只发生在**预览副本**上，原始引用被保留，因此编辑后能写回**真实路径**而不是 data URI。

**同时，磁盘上的产物仍是外链形态**（`<link rel="stylesheet" href="design-tokens.css">`）——**内联只发生在内存里的预览副本**。

> **一句话**：**磁盘上多文件（服务换肤与程序化改样式），预览时内联成单文档（服务 `srcdoc`）。两种形态并存。**

### 我们早期实现的两个错误

1. **改错了方向**：曾把预览从 `iframe.src` 改为 `fetch` + `srcdoc`，**理由是绕开认证**（iframe 无法携带自定义请求头）。但只做了"取 HTML 塞进 `srcdoc`"，**没有内联依赖** → 令牌全部失效。
2. **换错了代价**：用"外置资源全部失效"（大问题）换掉了"认证不便"（小问题）。而认证本不需要这样绕——参考方案证明：**预览走内存根本不需要认证，下载走 header token 即可**。

### 由此推出的约束

1. **预览渲染前必须内联**：令牌 CSS → `<style>`；外链图片 → data URI；并保留原始引用属性（供编辑写回）
2. **编辑器的 iframe 需 `sandbox="allow-same-origin"`**，否则读不到 `contentDocument`，无法选中元素（议题 5）
3. **仍需一条真实 URL 路由**，供下载与"直接查看产物"使用；该路由**用 header token 认证**（因为是 `fetch`，不是 iframe 导航）


## 5. 子项 2.3 · 访问路由与认证 ✅

### 参考方案的完整机制（实测其代码）

| 项 | design 的做法 |
|---|---|
| **外壳与 token** | Shell HTML 里放占位符 `__IPOLLOWORK_DESIGN_STUDIO_TOKEN_VALUE__`，服务端**替换成进程级随机 token** 后返回 |
| **API 认证** | `handleApi()` 开头调 `requireToken()`，校验 header `x-ipollowork-design-token` |
| **产物文件路由** | `/raw?workspaceId=X&path=design/…`，**有意不做 token 校验** |
| **Referer 防护** | Shell 响应带 `referrer-policy: same-origin` |
| **边界防护** | `safeRelativePath()` 强制路径落在 `design/` 前缀内，越界 403；拒 `..`、`\0`、绝对路径 |
| **客户端取文件** | `downloadWorkspaceFile()` → `fetch('/raw?…', { headers: { 'x-…-token': … } })` ——**用 `fetch` 所以能带 header** |

### 关键洞察：`/raw` 的 token 豁免只针对 iframe 导航

参考方案里 `/raw` 被**两种方式**访问：

1. **iframe 导航**（早期形态）→ 无法带 header → 因此豁免 token
2. **`fetch` 读取**（当前形态）→ **带 header token** → 认证正常

**所以"产物路由不能认证"这个结论是错的**——取决于访问方式。既然 2.2 已定"预览走内存 + `srcdoc`"，产物路由的访问者就只剩 `fetch`，**完全可以要求 header token**。

### 我们的路由设计

```
/canvas/studio/                              外壳界面（返回 HTML，内含替换后的 token）
/canvas/api/*                                API：要求 header x-canvas-token
/canvas/a/<workspaceId>/<产物名>/<相对路径>   产物文件：要求 header token（供 fetch）
```

### 认证方式

| 项 | 做法 |
|---|---|
| **token 传递** | Shell HTML 占位符 → 服务端替换为进程级随机 token（照抄 design） |
| **API 与产物路由认证** | 校验 header `x-canvas-token` |
| **URL 不带凭据** | 实测：query 带 token 会出现在 `Referer` 里（`…/artifact/index.html?token=…`）→ **不用** |
| **Referer 防护** | Shell 响应带 `referrer-policy: same-origin`（照抄 design） |
| **边界** | 强制路径落在 `canvas/` 前缀内，拒 `..`、`\0`、绝对路径（照抄 design） |

### 比参考方案多一处增强：`Sec-Fetch-Site` 校验

**为什么加**：参考方案的 `/raw` 无任何认证，任何网页都能发**跨站 GET** 去请求本地文件。虽然同源策略阻止**读取响应**，但**请求本身会发出**。加一次校验即可拒掉。

**实测该头确实存在**（真实 Chrome，产物路由收到的请求）：

| 请求 | `Cookie` | `Sec-Fetch-Site` | `Sec-Fetch-Mode` |
|---|---|---|---|
| `/artifact/index.html` | （带） | `same-origin` | `navigate` |
| `/artifact/design-tokens.css` | （带） | `same-origin` | `no-cors` |

**做法**：产物路由校验 `Sec-Fetch-Site: same-origin`；缺失或为 `cross-site` 时拒绝。

> 注意：`Cookie` 那列是早先一次候选方案（HttpOnly Cookie）的实测遗留。**该方案已否决**——参考方案证明 header token 足够，加 cookie 是多余的复杂度。

### 由此确定的约束

1. **外壳负责种 token**（占位符替换），客户端从 HTML 里取出并放进请求头
2. **API 与产物路由统一用 header token 认证**
3. **预览不经过路由**（2.2 已定走内存 + `srcdoc`），因此不受这些认证约束
4. **产物路由叠加 `Sec-Fetch-Site` 校验**，堵住参考方案的跨站 GET 缺口


## 6. 子项 2.4 · `data-*` 寻址层 ✅

### 参考方案的实测机制

**关键代码**（来自 Studio，通用元素定位）：

```js
// 纯 nth-of-type 路径，不依赖任何 data 属性
const be = ($) => {
  const Q = [];
  let oe = $.hasAttribute(N) ? $.parentElement : $;
  for (; oe && oe !== document.body;) {
    const ie = oe.tagName.toLowerCase();
    let ke = 1, Ne = oe.previousElementSibling;
    for (; Ne;) { Ne.tagName === oe.tagName && !Ne.hasAttribute(N) && (ke += 1); Ne = Ne.previousElementSibling; }
    Q.unshift(`${ie}:nth-of-type(${ke})`);
    oe = oe.parentElement;
  }
  return ["body", ...Q].join(" > ");
};

// 定位器可反查
if (Q.type === "select-locator") { document.querySelector(Q.locator) }
```

产出的定位器形如 `body > section:nth-of-type(2) > div:nth-of-type(1) > h2:nth-of-type(1)`。

编辑期为元素打**临时**标记：`setAttribute(N, "true")` 与 `setAttribute(y, String(i + 1))`。

### 属性分三类

| 类别 | 属性 | 谁在读 | 生命周期 |
|---|---|---|---|
| **A. 自动生成的临时标记** | `data-…-primary`（编辑编号） | 编辑器 | **临时**，保存前剥除 |
| | `data-…-preview-src`（图片原引用） | 预览内联 | **临时**，保存前 `removeAttribute` |
| **B. 模型可写的语义标记** | `data-ipw-theme-role="page\|card\|heading"` | **主题注入层**（启发式选择器之一） | 永久 |
| | `data-ipw-text`×53、`data-ipw-brand-slot`×24 | **没有任何程序读** | 永久，纯标记 |

### 三条关键判断

1. **编辑所需的属性是自动生成的**（`nth-of-type` 路径 + 临时编号），**不要求模型写任何东西**
2. **主题所需的属性是可选启发式提示**：主题注入层用
   `:where(h1, …, [role="heading"], [data-ipw-theme-role="heading"], .title, .headline, …)`
   **取并集**——**语义标签本身就已命中**，`data-*` 只提高命中率
3. **保存前必须剥除临时标记**——参考方案明确做了 `removeAttribute("data-…-preview-src")`

### 我们的决定

| 项 | 决定 |
|---|---|
| **前缀** | **`data-cv-*`**，与 `--cv-*` 令牌前缀统一，且与参考方案的 `data-ipw-*` 隔离（同装一页不冲突） |
| **是否保留"模型可写标记"层** | **保留** |
| **命名空间** | **自动生成的标记与模型可写的标记必须分开**（照抄参考方案的做法） |
| **与参考方案的差异** | 参考方案的 `data-ipw-text` **没有任何程序读**（Studio 里出现 0 次），纯装饰。**我们保留这一层，就要求编辑器真的读它** |

### 属性清单

**自动生成（临时，保存前剥除）**

| 属性 | 作用 |
|---|---|
| `data-cv-el` | 编辑期为元素分配的编号；用于编辑器的选中与定位 |
| `data-cv-preview-src` | 预览内联时保存图片的**原始引用**，供写回真实路径而非 data URI |

**模型可写（永久）**

| 属性 | 作用 | 与参考方案的差异 |
|---|---|---|
| `data-cv-slot="<名称>"` | 给可替换内容命名。**编辑器读取它，在选中该元素时把名称呈现出来**，使"改这一块"有明确指向 | 参考方案的 `data-ipw-text` 无人读；**我们的要被读**，否则不保留这一层 |
| `data-cv-lock` | 标记不可编辑元素（编辑器据此拒绝选中/修改） | 参考方案有 `data-ipw-locked`，但**只有 1 处使用** |
| `data-cv-brand` | 品牌位（logo、站名等替换点） | 对应参考方案的 `data-ipw-brand-slot` |

**不引入的**

| 不引入 | 原因 |
|---|---|
| `data-cv-theme-role` | 我们的令牌注入**可以做得更保守**：只依赖语义标签与 ARIA role 足够覆盖常见情形，不必要求模型额外标注 |
| 任何"纯装饰性"标记 | 若无程序读取，就不该要求模型写 |

### 由此确定的约束

1. **模型只写语义 HTML 即可**；`data-cv-*` 是**可选增强**，不写也能被编辑与换肤
2. **编辑器必须自动生成定位器**（`nth-of-type` 路径式），不依赖模型标注
3. **预览内联与编辑编号是临时态**，**保存产物前必须剥除**——产物文件里不应留下这些痕迹
4. **模型可写标记必须被读**：`data-cv-slot` 若不参与编辑器行为，就应当从规范中删除（避免变成参考方案那样的死标记）

## 7. 子项 2.5 · 伴随文件清单 ✅

### 参考方案的文件集

一个项目目录里**只有四个文件**：

| 文件 | 作用 |
|---|---|
| `index.html` | 页面（入口） |
| `design-tokens.css` | 令牌层（可换肤） |
| `brief.json` | **需求留痕**：`{ title, createdBy }` |
| `manifest.json` | 元信息：`category` / `style` / `tags` / `designSystem` / `applyChecklist` / `entry` / `cover` / … |

**没有的东西**：历史目录、锁文件、交互声明文件。

`ensureFile(resolve(directory, …))` 只创建前三个；`manifest.json` 另行写入。

### 我们的决定

**四个都要，元信息文件名为 `manifest.json`。**

```
canvas/<产物名>/
  index.html            页面（入口）
  design-tokens.css     令牌层
  brief.json            需求留痕
  manifest.json         元信息
```

### `manifest.json` 的字段（我们自己的 schema）

参考方案的 manifest 字段偏"模板目录"（`designSystem` / `applyChecklist` / `cover`），**我们按自身需要定义**：

```jsonc
{
  "schemaVersion": 1,
  "name": "pricing-page",          // 产物名（与目录名一致）
  "title": "云枢定价",              // 展示名
  "createdAt": "2026-09-29T15:59:14.000Z",
  "updatedAt": "2026-09-29T16:29:09.000Z",
  "entry": "index.html",           // 入口文件（产物可以只是一个组件，故显式声明）
  "tokens": "design-tokens.css",   // 令牌文件
  "brief": "brief.json",           // 需求留痕文件
  "interactions": null             // 交互声明文件；⬜ 待议题 3 定
}
```

| 字段 | 必要性 |
|---|---|
| `schemaVersion` | 让将来能演进而不猜 |
| `name` / `title` | 目录名与展示名分离（目录名必须是安全字符串，展示名可以是任意中文） |
| `createdAt` / `updatedAt` | 时间线；同时也用于"最近修改"排序 |
| `entry` | **产物可以只是一个组件**（`01` §6），因此入口文件名必须显式声明，不能写死 `index.html` |
| `tokens` / `brief` | 显式声明，避免程序里散落硬编码文件名 |
| `interactions` | ⬜ **待议题 3 定**（交互如何声明）。此处先占位，见 §9 |

### 不做"导出单文件"

参考方案没有此功能（它的导出是 PPT/PDF/图片，走 pptxgen / jspdf / html2canvas）。

**我们的决定：不提供。** 要交付产物就交付整个目录。

> 记录一个被否决的备选：曾考虑"提供导出单文件"以找回"拷给别人就能用"的诉求。**已否决**——议题 1 已确认"单个 HTML 文件"指的是**一个页面**而非文件数量；多文件形态是为了换肤与程序化改样式，不应为了携带便利而引入第二套形态。

## 8. 子项 2.6 · 版本管理程度 ✅

### 参考方案的真实水平

| 能力 | 参考方案 |
|---|---|
| **保存** | 写文件：**原子替换**（临时文件 + `rename`）+ **`mtime` 冲突检测**（不一致则 409） |
| **撤销** | **前端内存栈**——服务端 `undo`/`redo`/`history` 出现次数均为 **0**，`localStorage` 11 处仅存主题偏好，无 `indexedDB` |
| **版本历史** | **没有**。`revision` 只是 `${mtimeMs}-${size}`，不是历史标识 |
| **回退到任意一版** | **做不到** |

**含义**：刷新页面即失去撤销栈；关掉 Studio 后无法回到任何先前状态。

### 我们的决定：每个产物一个独立的 git 仓库

```
canvas/<产物名>/
  .git/                 该产物独立的版本历史
  index.html
  design-tokens.css
  brief.json
  manifest.json
```

| 项 | 做法 |
|---|---|
| **历史载体** | 目录内的 `.git`（**不挂在任何外层仓库上**） |
| **提交时机** | 每次生成成功、每次修改成功、每次可视化编辑保存 |
| **提交信息** | 人类可读 + 可追溯：例如 `生成产物：<标题>；<块/交互概要>` / `修改：<用户需求原文>` |
| **回退** | 从历史版本取回内容并**作为一次新提交**写入（保留"曾回退过"这一事实） |
| **携带性** | **拷贝整个目录即带走全部历史**（`.git` 就在目录内） |

### 为什么选 git 而不是自实现历史文件

| 理由 | 说明 |
|---|---|
| **成熟** | diff、回退、分支、历史查询全部现成，无需自己实现与测试 |
| **拷贝即携带** | `.git` 在产物目录内，天然满足"拷走目录就带走历史" |
| **可审计** | 每次改动的完整内容与时间线 |
| **不再造轮子** | 自实现 `.history/<时间戳>.html` 会重复 git 已解决的问题，且容易在并发、清理、体积增长上出错 |

### 需要注意的边界

| 边界 | 处理 |
|---|---|
| **临时文件不得入库** | 忽略产物目录内的临时态文件（编辑期标记、锁、缓存） |
| **不碰外层仓库** | 产物目录可能在某个外层 git 仓库内；**产物自己的 `.git` 独立运作，不得对外层仓库做任何操作** |
| **提交前剥除临时态** | 与 `data-cv-*` 临时标记（§6）一致：产物文件里不应留下编辑/预览痕迹 |
| **回退是新增提交** | 不做 `reset`/`checkout` 式的历史改写，避免"历史被抹掉" |

## 9. 子项 2.7 · 目录命名规则 ✅

### 参考方案的命名

| 项 | 参考方案 |
|---|---|
| 前缀 | **固定 `design/`**（`safeRelativePath(value, prefix = "design/")`） |
| 目录名 | `projectId`，实际为 `session-<sessionId>` |
| 一个会话能放几个 | **一个** |
| 可读性 | **不可读**——看目录名无法知道里面是什么 |

### 我们的决定

| 项 | 决定 |
|---|---|
| **根目录** | **`canvas/`**（与插件名一致） |
| **目录名** | **产物名**，**允许中文** |
| **一个工作区能放多少产物** | **任意多个** |

```
<工作区>/canvas/<产物名>/
  index.html
  design-tokens.css
  brief.json
  manifest.json
  .git/
```

### 目录名的规范化规则

**允许中文意味着必须显式处理跨平台与工具链的编码问题**，不能只靠"能建目录"就通过。

| 规则 | 内容 |
|---|---|
| **允许字符** | Unicode 字母与数字、`-`、`_`、`.`、中文等宽字符 |
| **禁止字符** | 路径分隔符 `/` `\`；控制字符（`\0`–`\x1f`）；Windows 保留字符 `< > : " \| ? *` |
| **禁止的值** | `.`、`..`、空字符串、纯空白 |
| **禁止形式** | 绝对路径；前导或尾随空白与点号（避免 Windows 与 macOS 的静默归一化差异） |
| **NFC 归一化** | 名称先做 Unicode NFC 归一化再使用，**避免"看起来一样但字节不同"的两个目录** |
| **长度上限** | 64 个字符（按码点数计） |
| **大小写** | 保留原样写入，**但重名检测按大小写不敏感**（Windows 与 macOS 默认如此），冲突时报错 |
| **重名** | 已存在则报错，**不静默覆盖、不自动改名** |

**不允许的**：空名、`.`、`..`、`a/b`、`a\b`、`a;b`、含换行或制表符、前导/尾随点号或空白。

### 展示名与目录名分离

| | 载体 | 允许中文 | 约束 |
|---|---|---|---|
| **目录名** | 文件系统 | ✅ | 上文全部规则；**必须能被安全地放进 URL 路径与 git** |
| **展示名** | `manifest.json` 的 `title` | ✅ 任意文本 | 仅用于 UI 显示 |

**分离的理由**：目录名同时要充当 URL 片段与 git 路径，约束必须比其他字段更严；而"看得懂"的需求由展示名满足。

### 中文目录名带来的三个具体注意事项

议题讨论中确认"允许中文"，因此实现时必须处理以下三点，**不能默认它们不存在**：

1. **URL 编码**：目录名进入产物路由（`/canvas/a/<workspaceId>/<产物名>/…`）时必须正确百分号编码与解码；**解码后再做路径校验**，避免用编码形式绕过边界检查
2. **git 路径引用**：提交时必须按**字面路径**引用文件（而非通配符或正则），并确保 git 的 `core.quotepath` 设置不会让中文路径显示成转义序列而影响人工核对
3. **文件名长度与终端显示**：中文在部分终端下按双宽显示；长度上限按**码点**计，避免按字节计导致中文名可用长度骤减

### 为什么可以在一放多个产物

用户需求里有"**可以自由选择产物并进行修改编辑**"——这要求列表里有多个可选项。参考方案一个会话只能有一个设计，无法满足该需求。
