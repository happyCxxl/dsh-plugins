# 07 · 实施计划

> **状态：🟡 讨论中。** 依据 [`docs/v2/`](README.md) 的六个议题定稿。
> **本文回答四件事**：代码放哪（A）、每一步怎么做（B）、**每一步之后产出对不对**（B）、**为什么这么选**（C）。

## A. 运行时架构

### A.1 代码结构

```
lib/
  index.js              插件入口：声明 inject、装配路由与工具、注册 client 视图
  routes.js             HTTP 路由：外壳、产物、API
  artifacts.js          产物目录管理：校验产物名、创建目录、读写四个文件、路径边界
  manifest.js           manifest.json 的 schema 与读写
  interactions.js       interactions.json 的 schema 与读写
  tokens.js             令牌文件：21 个令牌的定义、默认值、边界标记读写
  checks/
    step-checks.js      流水线每一步的产出检查（S1–S8）
    render-check.js     渲染检查（S9，真实浏览器）
  browser/
    cdp-pipe.js         CDP over pipe 传输（见 06 §2）
    cdp-driver.js       把"打开页面/取值"翻译成 CDP 命令
  agent/
    tools.js            canvas_generate 工具定义（03 §6）
    brief.js            子代理提示词组装
    assets.js           SKILL.md 与 references/ 的内置副本（打包时嵌入）
  versioning.js         产物 git 仓库：初始化、提交、历史、回退
  studio/
    shell.js            外壳页面（列表 + 预览 + 属性面板）
    editor.js           编辑器：选中、属性面板、#cv-edits 读写、内存撤销栈
client.js               DSH client 接入：注册 conversation.view
```

### A.2 谁调谁

```
用户在对话里说要页面
  ↓
模型调用 canvas_generate（工具）
  ↓  工具带 exec.agent（当前会话活 Agent）—— 这是子代理派发的必要条件（06 §1.6）
子代理：按提示词写四个文件到产物目录
  ↓
流水线 S1–S8：每一步之后检查该步产出
  ↓
S9：渲染检查（真实 Chrome）
  ↓
git 提交
  ↓
界面（conversation.view）刷新列表 → 用户看到页面
```

**为什么生成走子代理**：用户需求原文要求"不污染主会话上下文"。子代理完成写作，主会话只收到一行摘要。

**为什么必须有 `exec.agent`**：`06` §1.6 实测——`SubagentStartRequest.parent` 必填活跃 Agent；HTTP 路径没有它，伪造会被拒。**这是"能力必须做成工具"的硬约束，不是设计偏好。**

### A.3 依赖策略

**零运行时依赖。** 只用 Node 内置模块（`node:fs`、`node:http`、`node:child_process`、`node:path`、`node:crypto`）。

理由：
- 插件是 bundle 层，装进别人的 node_modules；引入依赖会与宿主版本冲突
- 参考方案（Archify）同样宣称零依赖
- 唯一需要 CDP 客户端，**自己写**（约 300 行，`06` §2 已把关键事实记全）

## B. 流水线：九步

**通用约定**：

| 项 | 约定 |
|---|---|
| **工作目录** | 模型**直接写目标目录** `canvas/<产物名>/`（不是临时目录） |
| **失败行为** | **就地修正**（用户确认的"乙"）：某步产出不对 → 把问题反馈给模型 → 模型改自己刚写的文件 → 重跑该步检查。**这是"写作过程内的返工"，不是"交付后的门禁重试"** |
| **修正上限** | 每一步**最多 2 次**就地修正；超限则停下报告（避免死循环） |
| **交付判据** | git 提交之前**不落"正式"状态**——提交是"这个产物可用"的标志 |
| **检查独立性** | 每一步的检查**单独可跑、单独可报告**，不依赖后续步骤 |

### S1 · 确定产物名与目录

| 项 | 内容 |
|---|---|
| **输入** | 用户需求；模型建议的产物名 |
| **动作** | 校验产物名 → 创建目录 → 初始化 git 仓库（空仓，尚无提交） |
| **产出** | `canvas/<产物名>/`、`canvas/<产物名>/.git/` |
| **检查** | ① 目录名通过 `02` §9 全部规则（NFC、禁字符、禁 `.`/`..`、禁前导尾随空白与点号、≤64 码点、**大小写不敏感重名检测**）② 目录**此前不存在**（已存在则报错，不覆盖）③ `.git` 成功初始化且**不是**外层仓库的一部分 |
| **失败** | 名字不合规 → 报告具体违反哪条，请模型改名；已存在 → 报告并**要求模型另选或明确要求覆盖**（不静默覆盖） |

**技术方案**：`artifacts.js` 暴露 `validateArtifactName(name)` 与 `createArtifactRoot(root, name)`。名称校验用 **Unicode 属性类**（`\p{L}`/`\p{N}`）而非手写字符集，避免漏字符。

**为什么先建 `.git`**：让"每个产物是独立仓库"从第一步就成立（`02` §8）。若等提交时再建，会出现"产物目录在某个外层仓库里"的窗口期。

### S2 · 写令牌

| 项 | 内容 |
|---|---|
| **输入** | 需求里的气质/配色线索；`01` §7.4 的 21 个令牌默认值 |
| **动作** | 写 `design-tokens.css`：边界标记 + `:root` + 21 个令牌 |
| **产出** | `design-tokens.css` |
| **检查** | ① 文件存在且非空 ② `/* cv-theme:start */` 与 `/* cv-theme:end */` **各恰好出现一次且顺序正确** ③ 边界内是**一个合法的 `:root` 规则**、括号配平 ④ 21 个令牌**齐且不多不少**（按 `01` §7.4 清单逐一核对）⑤ 值合法：颜色为十六进制、字体为非空字符串、数值型在合理范围 ⑥ 无未闭合注释 |
| **失败** | 报告缺哪个令牌 / 哪个值不合法 / 标记何处不成对 → 模型改文件 → 重跑 |

**技术方案**：`tokens.js` 里维护**令牌清单常量**（名字、类型、默认值），检查器**按清单核对**而不是"看有没有 `var(--cv-`"。**边界定位用注释正则**（照抄参考方案做法，`02` §7 已定）。

**为什么不用 CSS 解析库**：零依赖原则；且我们只需**定位边界 + 逐条读令牌**，正则足够（参考方案也这么做）。

### S3 · 写交互声明

| 项 | 内容 |
|---|---|
| **输入** | 需求；`03` §5 的场景引导 |
| **动作** | 判定是否要交互 → 写 `interactions.json`（或据实不写） |
| **产出** | `interactions.json`（可能存在，也可能按声明不写） |
| **检查** | ① 若非空：`schemaVersion` 存在；每条有 `id`、`name`、非空 `trigger` 数组 ② `id` 与 `name` **各自文件内唯一** ③ 所有动作在 `03` §4.5 **白名单**内 ④ 动作参数合法（`wait.ms ∈ [0,5000]`；`type`/`clearAndType`/`setValue`/`select` 有 `value`；`press` 有 `key`；`hotkey` 有 `keys` 数组；`drag` 有 `to`；`dragBy` 有 `dx`/`dy`；`scrollTo` 有 `selector`；`scrollBy` 有 `dy`）⑤ 每个动作有 `selector`（`wait` 除外） |
| **失败** | 报告具体哪条交互的哪个字段 → 模型改 → 重跑 |

**技术方案**：`interactions.js` 维护**动作白名单表**：`动作名 → { 必填参数, 可选参数, 参数类型 }`。检查器遍历该表，**不为每个动作手写 if**。

### S4 · 写页面

| 项 | 内容 |
|---|---|
| **输入** | 需求；S2 的令牌；S3 的交互声明 |
| **动作** | 写 `index.html`：结构 + 样式 + 行为；引用令牌；对交互打挂钩 |
| **产出** | `index.html` |
| **检查** | ① 单文档（有 `<!DOCTYPE html>`、`<html>`、`<head>`、`<body>`）② 有 `<main>` 且有 `<title>` ③ **所有 `href`/`src` 指向本地相对路径、`#` 锚点或 `data:`**（无 `http(s)://`、无 `//` 协议相对）④ **令牌引用前缀与 S2 一致**（`var(--cv-…)`）⑤ **每个交互 id 都有 `data-cv-interaction="<id>"`，且至少一个 `data-cv-effect="<id>"`** ⑥ **无临时态标记**（`data-cv-el`、`data-cv-preview-src`）⑦ 引用 `design-tokens.css` 与 `interactions.json`（如声明了交互）时路径正确 |
| **失败** | 报告具体哪个引用/哪个 id 缺挂钩 → 模型改 → 重跑 |

**技术方案**：**自写轻量 HTML 扫描器**（不用正则，理由：属性值里可含 `>`、引号可混用、注释与 `<script>` 里可能有像标签的文本——正则会给假阳性）。扫描器按状态机走，正确处理引号、注释、`CDATA` 与原始文本元素。

> 这是本文档唯一"看起来可以省但省不掉"的组件。参考方案同样自写扫描器。

### S5 · 写需求留痕

| 项 | 内容 |
|---|---|
| **输入** | 用户的原始需求文本 |
| **动作** | 写 `brief.json`：`{ title, brief, createdBy, createdAt }` |
| **产出** | `brief.json` |
| **检查** | ① 合法 JSON ② `brief` 非空（**这是这一步存在的唯一理由**：记录"这一版是为满足什么需求做的"）③ `createdAt` 为合法 ISO 时间 |
| **失败** | 报告缺哪个字段 → 模型改 → 重跑 |

**技术方案**：`brief` 字段**存用户需求原文**（而非模型转述），这样版本历史里能追溯"当初到底要什么"。

### S6 · 写元信息

| 项 | 内容 |
|---|---|
| **输入** | 前面各步的产出；产物名 |
| **动作** | 写 `manifest.json` |
| **产出** | `manifest.json` |
| **检查** | ① 必填字段齐（`schemaVersion`、`name`、`title`、`createdAt`、`entry`、`tokens`、`brief`、`interactive`）② **`name` 与目录名逐字符一致**（含 NFC 归一化后比较）③ `entry`/`tokens`/`brief` **指向的文件真实存在** ④ `interactive: true` 时 `interactions` 字段存在且指向真实文件；`false` 时 `interactions` 为 `null` **且 S3 未产出文件** ⑤ `createdAt`/`updatedAt` 为合法 ISO |
| **失败** | 报告字段级问题 → 模型改 → 重跑 |

**技术方案**：`manifest.js` 定义 schema 与检查器。**`name` 与目录名的一致性用 NFC 归一化后比较**——防止"看起来一样但字节不同"（`02` §9）。

### S7 · 跨文件一致性

| 项 | 内容 |
|---|---|
| **输入** | S2–S6 的全部产出 |
| **动作** | 交叉核对（不改文件） |
| **产出** | 一致性结论（无新文件） |
| **检查** | ① **S2 ↔ S4**：HTML 里引用的令牌名**全部**在 `design-tokens.css` 里定义 ② **S3 ↔ S4**：`interactions.json` 的每个 `id` 在 HTML 里都有触发元素；反向：HTML 里的每个 `data-cv-interaction` 值都在声明里（**不允许有声明外的交互标记**）③ **S6 ↔ 全部**：manifest 的所有文件引用有效 ④ **S3 ↔ S6**：交互文件的存在性与 `interactive` 一致 |
| **失败** | 报告是哪两个文件之间的哪个不一致 → 模型改 → 重跑 |

**为什么单列一步**：**"文件之间不一致"是一类独立缺陷**——每个文件单独看都合法，合起来才错（例如 HTML 引用了 `--cv-color-brand`，而令牌文件里没有）。若打散进各步，这类问题会没有明确归属。

### S8 · 版本提交

| 项 | 内容 |
|---|---|
| **输入** | 全部产出 |
| **动作** | 暂存四个文件 → 检查暂存内容 → 提交 |
| **产出** | git 提交（`.git/` 内有历史） |
| **检查** | ① `.git` 在产物目录内、`git status` 无"在仓库外"的迹象 ② **暂存内容不含临时态**：无 `data-cv-el`、无 `data-cv-preview-src`；`#cv-edits` 若存在**必须为空**（初次生成时）③ 提交信息可读（含需求摘要）④ 只暂存**四个文件**，不 `add -A` |
| **失败** | 报告暂存了哪些不该有的内容 → 清理 → 重新提交 |

**技术方案**：`versioning.js` 用 `execFile('git', [...])` 而非 shell 字符串（避免中文路径与空格被 shell 拆词）。**`git add` 显式列四个文件**（不用 `-A`，遵守仓库纪律）。

**中文路径处理**（`02` §9、本次实测确认）：`core.quotepath` 默认 `true`，会把中文路径显示成八进制转义。**提交时用字面路径引用**，并在仓库级设置 `core.quotepath=false`，让历史可人工核对。

### S9 · 渲染检查

| 项 | 内容 |
|---|---|
| **输入** | 四个文件（完整产物） |
| **动作** | 用真实 Chrome 打开产物，采集检查数据 |
| **产出** | 检查结论；**无产物变更** |
| **检查** | `04` §3 第二道：① 页面打开并渲染（`<main>` 有内容、非空白）② 无未捕获 JS 异常 ③ 无 console error ④ 无资源加载失败 ⑤ **无横向溢出**（`scrollWidth <= clientWidth`）⑥ 多视口成立（移动/桌面/宽屏） |
| **失败** | 报告失败原因（异常文本 / 失败的资源 / 溢出尺寸）→ 模型就地修正 → 重跑。**浏览器不可用时报告"渲染未经检验"，产物仍产出但不提交？** → 见 C.7 |

**技术方案**：
- **内联依赖后注入 `srcdoc`**（`02` §4）：令牌 CSS → `<style>`，图片 → data URI（保留 `data-cv-preview-src` 供后续编辑写回）
- **CDP over pipe**（`06` §2.1）：fd 3 写 / fd 4 读，**NUL 分隔**
- **两个流都挂 `'error'` 监听**（`06` §2.2）
- **独立 `--user-data-dir`**、**Windows 杀进程树**（`06` §2.3、§2.4）
- **不截图**（验收由人做）

> **为什么 S9 要真实浏览器而不是静态扫描**：`04` §4 已把"交互行为验证"降为模型规则，但**"页面能不能开"**没法靠静态分析判断——JS 在运行时才报错，溢出要真实布局才算得出。

## C. 技术方案与取舍

### C.1 为什么"模型直接写目标目录"而不是"写临时目录再搬"

| | 临时目录 → 搬 | **直接写目标目录** |
|---|---|---|
| 模型改自己刚写的文件 | 可以 | 可以 |
| 中途失败留下的东西 | 临时目录里的半成品 | **目标目录里的半成品** |
| 用户能否看到中间过程 | 看不到 | **能看到** |
| 复杂度 | 需要搬迁与清理逻辑 | **无额外逻辑** |

**选直接写**。理由：**"半成品"不是问题**——git 提交才是"可用"的标志，未提交的产物目录一眼可辨。而"用户能看到中间过程"是**优点**（符合"在结果上后续修改"的立场）。

**代价（明确接受）**：失败时产物目录会留下不完整的文件。由用户在界面上可见（界面标注"未提交"）。

### C.2 为什么自写 HTML 扫描器

**用正则会给出假阳性**：属性值里可含 `>`（`title="a > b"`）、引号可单双混用、注释与 `<script>` 里可能有像标签的文本。**一旦用户学会"这条报错是误报"，整个检查体系就失去可信度。**

因此自写按状态机走的"够用正确解析"：正确处理引号、注释、`CDATA` 与原始文本元素（`script`/`style`/`textarea`/`title`）。

### C.3 为什么用 Unicode 属性类做名称校验

手写字符集（如"允许中文"）容易漏字符（会把日文假名、韩文、全角标点等漏掉）。用 `\p{L}`（字母）+ `\p{N}`（数字）+ 显式允许的标点，**覆盖面由 Unicode 保证**。

### C.4 为什么路由"只解码一次，再校验"

本次实测（见上文）：

```
url.pathname 保持百分号编码 → /canvas/a/ws/%E5%AE%9A.../index.html
只解码一次 → %2e%2e 仍是字面量，不构成 ..
解码两次   → ../../etc/passwd   ← 路径穿越
```

**方案**：`decodeURIComponent` **只调一次**，**解码后**再做路径边界校验（确保落盘路径仍在 `canvas/<产物名>/` 内）。**顺序不可颠倒**——先校验后解码等于没校验。

### C.5 为什么要"每步检查"而不只在最后检查

用户明确要求：**流程每一步的产出都要能验收**。

技术上的收益：**失败定位的精度**。若只在 S9 检查，一个"令牌名拼错"的错误会表现为"页面样式不对"，排查要回溯整个链路。逐步检查能直接指出"`--cv-color-brand` 在令牌文件里不存在"。

### C.6 为什么生成走子代理

**用户需求原文**："生成和修改页面时都需要通过子代理来触发，这是为了不污染主会话的上下文"。

技术上还有一条硬约束（`06` §1.6）：子代理派发需要**活跃的父 Agent**，而它只存在于**工具调用上下文**（`exec.agent`）里。**所以"生成"必须是工具，不能是 HTTP 路由。**

### C.7 一个待定：浏览器不可用时怎么办

`04` §5 定了"浏览器不可用 → 产物仍产出，但**明确标注渲染未经检验**"。但**这与 S8 的 git 提交冲突**：

| 选项 | 含义 |
|---|---|
| **甲** | 浏览器不可用 → **不提交**，产物留在目录里标注"未提交、未经渲染检验" |
| **乙** | 浏览器不可用 → **照常提交**，但在提交信息与界面里标注"渲染未经检验" |
| **丙** | 浏览器不可用 → **报错，不产出**（因为"页面能开"是本产品的底线） |

**我倾向甲**：与 `04` §5"不产出产物"的立场一致（提交 = 可用），且不会把未验证的东西标成"可用版"。**但这条需要你定。**
