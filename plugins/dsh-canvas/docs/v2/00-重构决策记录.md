# 决策记录：为什么从"spec 编译"转向"自由 HTML"

> **本文件记录重构的动因与前提，供 v2 各文档引用，避免每篇重复解释。**
> 本文描述的是**已废弃的旧路线**，只作为"为什么要改"的背景存在。

## 旧路线是什么

早期实现（见 `docs/` 根下的 SPEC.md / ARCHITECTURE.md）采取的是：

```
用户需求 → 模型写 JSON spec → 程序确定性编译出 HTML
```

模型**不写 HTML**，只写一份声明式 JSON；几何、布局、SVG、HTML 组装、样式全部由代码生成。当时的理由是"用确定性换取可靠性"——参考了对另一个方案（Archify）的分析结论：**它的可靠性来自消除自由度**。

## 这条路线的四个问题

### 1. 它把"手段"当成了"目的"

真实的用户需求（见 `01-背景与目标.md`）是：

> **任意场景 + 精美 + 动态可交互 + 可编辑 + 可版本管理**

"确定性编译"是为了达成"可靠"而选的一种**手段**。但落地时它变成了**目的本身**——渲染器只认自己预设的块类型和结构，于是：

- **"任意场景"做不到**：渲染器只有一套布局骨架，任何 spec 都渲染成同一种结构
- **"精美"做不到**：视觉质量上限被那一份手写样式表锁死

实测反馈：用户连续两次指出"和修改之前没有任何区别"。当时改的是字号、行高、间距（**规范**），而布局骨架、区块节奏、视觉语言（**风格**）从未变过。**在错误的维度上持续加码。**

### 2. 它错失了产品的核心命题

对照被参考的两个方案：

| 方案 | 精美 | 动态可交互 |
|---|---|---|
| deepseek-idesign | ✅ 29 个手工模板 + 令牌系统 | ❌ **29 个模板全部零功能交互**（无内联事件、无提交处理） |
| Archify | — | ✅ |

**"精美"和"可交互"是两件事，且没有现成方案同时做到。** 而旧路线把精力放在"如何让声明式编译更严谨"，**没有触及这个核心命题**。

### 3. 它做了一个未经确认的架构决定

"模型只能写 JSON"这个约束**从未作为待确认项提出**。用户只说过要"可靠的可交互 HTML"，并未要求放弃 HTML 自由度。这是一个**实现方式**的选择，却被当成了需求的组成部分，并在此后所有轮次里被当作既定前提。

### 4. 它把"精美"理解成了规范问题，而不是审美问题

这是转向过程中最后被查清、也最关键的一条。

旧实现为保证"精美"，投入了大量**规范工作**：建立字号阶梯（13 种杂乱字号收敛到 8 档）、配对行高（2 处补到 22 处）、把间距改为响应式 `clamp()`、拆分卡片与按钮圆角令牌。

**但用户连续两次的反馈都是"和修改之前没有任何区别"。**

调研 design 后找到原因：**它的"精美"来自一组人工选定的美学值，而不是规范。**

```js
// deepseek-idesign 插件内嵌的默认令牌
--ipw-color-bg: #f2f0eb;          // 米色底，不是纯白
--ipw-color-primary: #5b50e6;     // 有性格的深紫，不是默认蓝
--ipw-font-display: Georgia, serif;                    // 衬线标题
--ipw-card-shadow: 0 24px 70px rgb(24 20 14 / 10%);    // 大而柔的投影
```

**这四个决定贡献了绝大部分"高级感"。** 米色底 vs `#fff`、衬线 vs 无衬线、深紫 vs 默认蓝——这些是**审美选择**，不是**规范推导**。

**教训**：规范能让页面"不坏"，但**产生不了美**。在"不坏"这个维度上做到满分，"美"这个维度依然是零。**这是与"在错误的维度上持续加码"同源的一类错误，但更隐蔽——因为规范工作的每一步看起来都是正确的。**

## 新路线的立场

**产出是工作区里的真实 HTML 文件，agent 可以直接编写与修改它。**

- 模板只是**起点**，用来保证起点的精美度，**不是必须的**（可以从零写）
- **交互是本产品的存在理由**，不是附加功能
- 可靠性由**门禁与验证**提供（扫产物、在真实浏览器里跑交互），而不是由"限制模型表达力"提供
- **美学是审美决定，不是规范问题**：以一组人工选定的令牌值作为基线（见 `01-背景与目标.md` §7.4），**不提供任何预设结构或组件类**

## 附一：一个与"验证"有关的教训

在议题 2 定"预览方式"时，实测发现早期的一个修复**方向是错的**，而且**当时被判定为"已验证通过"**：

- 预览原本用 `iframe.src` 指向产物 URL（**正确**），但 iframe 无法携带自定义认证头
- 为绕开认证，改成了 `fetch` 取回 HTML + `iframe srcdoc` 注入
- **代价换错了**：`srcdoc` 的文档 `baseURI` **继承宿主页面**，于是产物里的相对路径 `href="design-tokens.css"` 被解析到宿主目录 → **外置令牌全部加载失败** → 背景、字体、圆角、投影、宽度全塌
- 而当时的验证**只检查了"HTML 内容出现在 iframe 里"**，因此"通过"了

**教训：验证必须检查目标效果（令牌解析成功、样式生效），而不是中间产物的存在。** "内容出现了"≠"页面正确"。

完整实测数据见 `02-产物形态.md` §4。

## 附二：一个与"研究方法"有关的教训

议题 2 里同一个问题犯了两次同类错误，值得单独记下来。

### 第一次：测出问题就下结论，没先查参考方案

**经过**：我实测发现"`iframe srcdoc` + 外链资源 = 令牌全部失效"，随即把结论写成 **"预览必须用 `iframe src` 指向真实 URL"**，并据此推导出一串约束（产物必须有可寻址路由、编辑器必须与产物同源…）。

**然后用户问了一句**：*"design 是怎么做的，如果 design 有现成的解法，你干嘛还要去自己解决方案"*

**去查之后发现**：参考方案的**编辑预览用的就是 `srcdoc`**，它靠**内联依赖**（令牌 CSS → `<style>`，图片 → data URI）绕开了 `baseURI` 问题，甚至留了 `data-*-preview-src` 属性保存原始引用以便写回。

**所以我的结论是残缺的**："`srcdoc` 不能用"是错的，正确的是"**`srcdoc` 可以用，但必须先内联依赖**"。而参考方案早已解决，我却在重新发明，还发明错了。

### 第二次：把"某种访问方式下的限制"当成了"路由本身的限制"

我曾判断"产物路由**不能**做 token 认证，因为 iframe 带不了 header"。查了参考方案才发现：它的 `/raw` 被**两种方式**访问——iframe 导航（豁免 token）与 `fetch` 读取（**带 header token**）。既然预览已改为走内存，产物路由的访问者就只剩 `fetch`，**完全可以要求 header token**。

### 共同规律

**两次都是同一个错误：先在自己造的场景里做实验，从实验结果直接推出"必须怎样"，而跳过了"参考方案是怎么做的"这一步。**

- 第一次的代价：得出错误结论，并据此推导出一串多余的约束
- 第二次的代价：把一个可选方案（HttpOnly Cookie）当成必需方案去设计

**这不是"没做调研"——我做了大量调研（读了 216 个文件、量了 29 个模板、解析了 7.5MB 的 bundle）。问题是调研的时机：我在"已经自己得出结论"之后才去查，于是查到的信息只能用来补注，而不是用来形成结论。**

**正确顺序**：**遇到设计问题 → 先查参考方案怎么解 → 再结合实测判断是否照抄、何处增强。**



## 什么被保留了

旧实现中与"如何产出 HTML"无关的能力**不因这次转向而作废**，包括：

- 门禁思路（单页契约、自包含、视口可达性——这些都只需扫 HTML，不依赖 spec）
- 真实浏览器验证交互的做法
- 产物目录与独立 git 版本化的做法
- 工作区目录约定

**这些会在后续议题里重新审视与确认，而不是默认继承。**
