## 3. 子项 4.1 · 校验清单 ✅

### 只留两道

#### ① 完整性（机械检查，不需要浏览器）

| 检查 | 判据 |
|---|---|
| 四个文件存在 | `index.html` / `design-tokens.css` / `brief.json` / `manifest.json` |
| manifest 合法 | 必填字段齐全；`name` 与目录名一致 |
| 引用有效 | `manifest.json` 的 `entry` / `tokens` / `brief` 指向的文件**确实存在** |

**为什么这算"必须"而不是"替人判断"**：**缺文件 = 产物不成立**，与质量无关。

#### ② 渲染检查（真实浏览器，跑一次）

| 检查 | 判据 |
|---|---|
| **页面能打开并渲染** | 文档加载成功；`<main>` 有内容；非空白页 |
| **无未捕获 JS 异常** | 无 uncaught error |
| **无 console error** | 控制台无 error 级输出 |
| **无资源加载失败** | 无本地引用的 404 |
| **无横向溢出** | `documentElement.scrollWidth <= clientWidth` |

**为什么这算"必须"**：**打不开 / 报错 / 横向溢出 = 页面是坏的**，与好看无关。

**执行环境**：真实 Chrome + CDP over pipe（不用端口、不截图）。浏览器不可用时见 §5。

### 为什么不更多

**门禁越多，越是在替人判断"可以了"**（§6）。而：

- 每个门禁都需要维护、需要处理误报
- **一旦用户学会"这条报错是误报"，整个校验体系就失去了可信度**
- 真正决定"能不能用"的是人，不是脚本

## 4. 子项 4.2 · 降级项 ✅

以下原本被设计成门禁，**现在降为"模型规则"（写进 Skill / 提示词，不再自动拦截）或直接删除**：

| 原门禁 | 降为 | 理由 |
|---|---|---|
| **自包含**（无外链、无网络调用） | 模型规则 | 人**离线打开**就立刻发现；不需要门禁先替人报错 |
| **单页契约**（无跨页导航、无 `meta refresh`） | 模型规则 | 同上 |
| **可访问性基线**（`alt`、标题层级、表单控件可访问名） | 模型规则 | 这是**质量**，不是**能不能渲染** |
| **令牌契约**（主题值必须走 `var(--cv-*)`） | 模型规则 | 编码规范 |
| **交互行为验证**（有变化、确定性、初始态≠终态、多视口） | 模型规则 | **人点一下就知道** |
| **确定性渲染**（同输入两次渲染字节一致） | **删除** | 只防实现者自己的重构回归，对成品无价值 |
| **版本提交** | **动作**，不是检查项 | 提交是流程步骤，不是校验 |

**降级的代价（明确接受）**：模型可能违反这些规则（例如偷偷引用一个 CDN），**门禁不会拦**。要等人打开产物时发现。**这正是"问题在结果上后续修改"的立场。**

### 关于自包含的一条说明

议题 1 §8 把"多页/路由"列为非目标、`01` §7 定了令牌外置。**自包含不再是门禁，但它仍是模型应当遵守的规则**——因为产物要能离线打开、能拷给别人。区别在于：**违反它不再阻断产出，而是表现为"人打开时发现加载不出东西"。**

## 5. 子项 4.3 · 失败处理 ✅

### 不重试

**用户明确要求：不需要重试。**

| 情形 | 行为 |
|---|---|
| 完整性不通过 | **不产出产物**；报告缺什么（精确到文件名与字段） |
| 渲染不通过 | **不产出产物**；报告失败原因（异常内容 / 失败的资源 / 溢出尺寸） |
| 浏览器不可用 | 静态产物仍可产出，但**必须明确标注"渲染未经检验"**；**不得声称已验证** |

**"不产出产物"的含义**：要么不落盘，要么落到临时位置且**不提交**。**不留半成品让人误以为可用。**

### 为什么不做修复回路

早期设计的回路是：门禁失败 → 诊断 → 有限轮次修复 → 重跑全部门禁。**现在取消**，理由：

1. **重试是为了无人值守**，而这里有明确的人
2. 失败本身就是最重要的信号：**打不开的页面不值得修，值得重来或由人指出方向**
3. 修复回路会掩盖真实的问题分布——"重试三次后过了"看起来是成功，实际说明生成能力不稳定

### 报告要求

| 项 | 要求 |
|---|---|
| 精确性 | 报失败必须精确到**文件 / 字段 / 元素 / 尺寸**，不能只说"校验失败" |
| 状态诚实 | 必须区分「自动检查通过」与「人工看过」；**不得声称没做过的检查** |
| 不夸大 | `skipped`（浏览器不可用）**不得**被表述为"通过" |

## 6. 子项 4.4 · 门禁边界 ✅

### 门禁不判"可以了"

| 门禁**做** | 门禁**不做** |
|---|---|
| 报"文件齐不齐" | 判"页面好不好看" |
| 报"页面能不能开、有没有报错" | 判"文案质量" |
| 报"有没有横向溢出" | 判"交互有没有意义" |
| — | **判"可以了"** |

**"可以了"永远由人判断。** 门禁只提供**事实**（文件在不在、页面开不开得了），不提供**结论**（能不能交付）。

### 自动检查与人工看过必须分开陈述

这是从参考方案（Archify）借来、且与本议题立场**不冲突**的一条原则：

> Passing one claim never implies the others. · **Never claim visual inspection you did not perform.**

**它不冲突的原因**：它约束的是**"不许夸大证据"**，而不是"替人做判断"。**恰恰相反——它把判断权明确留给人。**

因此报告里必须区分：

| 声明 | 含义 |
|---|---|
| 完整性检查 | 自动，可断言 |
| 渲染检查 | 自动，可断言（或 `skipped`） |
| 人工看过 | **只能由人声称**，模型不得代替 |

### 不做"四层主张"的完整机制

参考方案还区分了截图证据与感知评审两个更细的层级。**我们不需要**——因为我们**不做截图**、**不声称视觉质量**（验收由人做）。只保留"自动 / 人工"这一条分界。

## 7. 子项 4.5 · 声明一致性 ✅

`manifest.json` 的 `interactive` 与 `interactions.json` 的存在性不一致（声明有交互但没有声明文件，或声明无交互却有声明文件）：

**降为警告，不拦截。**

| 项 | 决定 |
|---|---|
| 是否阻断产出 | **否** |
| 是否报告 | **是**（警告） |
| 理由 | 不影响"能不能渲染"，因此不属于 §3 的两道门禁 |

**同理**：`data-cv-interaction` 的触发元素不可达、`interactions.json` 里的选择器命不中产物 DOM —— 这些都是**交互声明与产物不符**的表现，属于"人点一下就会发现"的范畴，**报警告，不拦截**。
